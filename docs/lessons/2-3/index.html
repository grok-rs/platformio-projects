Суперцикл: кілька справ одночасно без delay()

Одна задача, один цикл, жодного очікування — і плата водночас блимає, слухає кнопку й пише в Serial. Розберемо, як це працює і де ламається.

  • ≈ 25 хв читання
  • Потрібно: плата, 3 LED, 3 × 220 Ом, кнопка
  • Спершу: урок 2.1 (C++ для MCU)
  • Стенд: блокуюча прошивка
Я це знаю → до самоперевірки

01 Навіщо це

Плата блимає світлодіодом через delay(1000). Ви тиснете кнопку — нічого. Тиснете довше — спрацювало. Код наче правильний, кнопка справна. Насправді програма весь час чекає і дивиться на кнопку лише раз на секунду.

Уявіть кухаря, який поставив варитися яйця й 10 хвилин стоїть над каструлею із секундоміром. Суп на сусідній конфорці тим часом википає. Досвідчений кухар поглядає на годинник і обходить плиту по колу. Цей урок про те, як навчити плату працювати так само.

02 Після уроку ви зможете

  • пояснити, що саме зупиняє delay() на ESP32 і чому кнопка через нього «глухне»;
  • написати неблокуючий таймер now - last >= interval і пояснити, чому він переживає переповнення millis();
  • зібрати суперцикл із трьох незалежних задач: два LED з різними періодами, кнопка і Serial;
  • виміряти, скільки разів за секунду виконується loop() і скільки натискань губиться;
  • описати довгу дію як автомат станів, а не як ланцюжок пауз.

03 Розминка: згадаймо

04 Головні ідеї

delay() зупиняє вашу програму, а не чип

На ESP32 ваші setup() і loop() працюють у задачі FreeRTOS loopTask на ядрі 1. delay() — це vTaskDelay(): задача засинає, а ядро тим часом виконує інші задачі. Таймер далі рахує мілісекунди, переривання спрацьовують. Але весь ваш код у loop() стоїть на одному рядку: кнопку ніхто не читає, LED ніхто не перемикає.

ГоловнеПід час delay() ваш loop() сліпий і глухий, хоча чип не спить.

Суперцикл — це домовленість: кожна функція швидко повертається

Досвідчений кухар не стоїть біля каструлі: обходить плиту по колу і на кожній конфорці лише питає «вже?». Так працює суперцикл. loop() по черзі викликає короткі функції — pollButton(), updateLeds(), report(), — і кожна одразу повертає керування. Ядро робить до 240 мільйонів тактів за секунду, тож коло проходиться дуже часто, і здається, що все відбувається одночасно. Досить одній функції почати чекати — і зупиняється все коло.

ГоловнеЯк часто перевіряється кнопка, залежить від найповільнішої функції в циклі.

Опитування: глянути зараз — і далі

digitalRead() не чекає натискання: він повертає рівень саме в цю мить. Тому опитування ловить подію лише тоді, коли дивиться частіше, ніж подія триває. На малюнку крапки — моменти перевірки: рідкі пропускають коротке натискання, часті його ловлять.

Друге правило: реагуйте на зміну, а не на рівень. Із INPUT_PULLUP натиснута кнопка дає LOW. Запам’ятайте попередній стан і ловіть момент «було відпущено → стало натиснуто»:

bool down = digitalRead(BTN) == LOW;
// один раз на натискання:
if (down && !wasDown) onPress();
wasDown = down;

ГоловнеОпитування бачить лише те, що триває довше за проміжок між двома перевірками.

З часом не чекають — його вимірюють

millis() повертає кількість мілісекунд від старту плати. Замість «почекай 500 мс» кожен прохід питає: «скільки минуло від останнього разу?» Якщо досить — дія і новий відлік. Якщо ні — одразу далі. У кожної задачі своя змінна last, тому таймери не заважають один одному.

uint32_t lastA = 0;
void updateLedA(uint32_t now) {
  // минуло ≥ 500 мс?
  if (now - lastA >= 500) {
    lastA += 500;  // відлік від «сітки»
    toggle(LED_A);
  }  // інакше одразу назад у loop()
}

А що буде через 49,7 доби? millis() повертає 32-бітне беззнакове число. Після 4 294 967 295 мс (2³² − 1) воно знову стає 0, як механічний одометр після 999 999 км. Одне таке коло — 2³² мс ≈ 49,7 доби. Беззнакове віднімання теж рахує «по колу». Тому now - last завжди дає відстань від last уперед до now, навіть коли між ними нуль. А от last + interval може сам перескочити через нуль і стати малим числом, і тоді порівняння now >= last + interval помиляється. Перевірите в розділі 05.

ГоловнеПишіть тільки now - last >= interval, а час зберігайте в uint32_t.

Детальніше: last += interval чи last = now?

millis() рахує цілими мілісекундами. Якщо прохід циклу коротший за 1 мс, перша перевірка, яка бачить «минуло ≥ 500», трапляється саме тоді, коли now дорівнює last + 500. Тоді last = now і last += 500 дають те саме число, і дрейфу немає.

Інша справа, коли в циклі є повільна функція (як readSensor() на 40 мс у таймлайні). Прохід доходить до перевірки на кілька мілісекунд пізніше. last = now запам’ятовує цей пізній момент, і запізнення додається до наступного періоду. Запізнення на 2 мс у кожному періоді 500 мс дає 7200 періодів × 2 мс ≈ 14 с за годину. last += interval запам’ятовує момент, коли подія мала статися, тому сітка 0, 500, 1000… не зсувається.

Є й пастка: якщо цикл простояв довше за кілька періодів, += почне «надолужувати» серією швидких перемикань. У проєкті esp32-s3-embedded-cpp · blinker.h після += стоїть ще одна перевірка: якщо відставання досі більше за період, last = now. Для простого блимання LED зсув на кілька секунд за годину ніхто не помітить, тож там last = now теж годиться. Для годинника, звуку чи журналу вимірювань потрібна рівна сітка.

Довгу дію розбивайте на стани

Світлофор «червоний 3 с → зелений 3 с → жовтий 1 с», написаний через delay(), — це три паузи, під час яких плата нічого не чує. Автомат станів робить інакше: змінна state пам’ятає, де ми, а stateStart — коли сюди потрапили. Кожен прохід перевіряє лише одне: «чи вже час переходити?» Програма завжди знає, де вона, і ніколи не стоїть на місці. Торкніться схеми, щоб зупинити або запустити.

ГоловнеАвтомат — це «де я», «скільки я тут» і «коли переходити далі».

Код автомата світлофора 
enum class Light : uint8_t { Red, Green, Yellow };
Light state = Light::Red;
uint32_t stateStart = 0;

void enter(Light next, uint32_t now) { state = next; stateStart = now; showLight(next); }

void updateLight(uint32_t now) {
  const uint32_t inState = now - stateStart;   // скільки ми вже тут
  switch (state) {
    case Light::Red:    if (inState >= 3000) enter(Light::Green,  now); break;
    case Light::Green:  if (inState >= 3000) enter(Light::Yellow, now); break;
    case Light::Yellow: if (inState >= 1000) enter(Light::Red,    now); break;
  }                                            // ніде не чекаємо
}
Детальніше: ядро 3.x, сторожовий таймер і крок delay()

Наші проєкти зібрані на ядрі Arduino-ESP32 2.0.17. У ядрі 3.x тут нічого не змінилося: loopTask так само на ядрі 1, тік FreeRTOS — 1000 Гц.

Зайнятий loop() без жодного delay() плату не перезавантажує: сторож задач стежить лише за idle-задачею ядра 0, а для loopTask його вимкнено. Ядро 1 при цьому завантажене на 100 %, і для батарейних пристроїв це погано.

delay() рахує в тіках FreeRTOS: 1 тік = 1 мс. yield() — це не пауза: він лише пропонує планувальнику іншу готову задачу.

07 Типові помилки

    

      
delay() зупиняє весь мікроконтролер.

      
Зупиняється лише задача, яка його викликала. Таймери, переривання і задачі на ядрі 0 працюють далі.

      
У скетчі міні-лаби надрукуйте millis() перед delay(5000) і одразу після нього: друге число більше на ≈ 5000. Поки ваш loop() спав, таймер чипа рахував далі. Якби чип зупинявся, різниця була б 0.

    

    

      
now >= last + interval — те саме, що now - last >= interval.

      
У математиці так, а в 32-бітних числах ні: last + interval може переповнитися, і умова спрацює зарано або «застрягне».

      
Віджет «Переповнення millis()» у розділі 05: «за 500 мс до нуля» показує спрацювання зарано (повзунок до 500 мс), «за 1200 мс до нуля» — «застрягання» (повзунок понад 1200 мс).

    

    

      
if (кнопка натиснута) onPress(); — це обробка натискання.

      
Це обробка рівня: поки палець на кнопці, onPress() викликається в кожному проході, тобто тисячі разів. Натискання — це зміна: down && !wasDown.

      
У скетчі міні-лаби приберіть && !wasDown: лічильник натискань полетить угору.

    

    

      Ще дві помилки: «швидший loop» і точність millis()
      

      
Чим швидше крутиться loop(), тим краще.

      
Важливо інше: щоб найдовший прохід був коротший за найкоротшу подію. Понад це — лише порожні перевірки, які займають ядро на 100 %.

      
Міні-лаба: додайте в неблокуючий loop() delayMicroseconds(1000). Частота циклу впаде до ≤ 1000 проходів/с, а кнопка працює так само: натискання триває десятки мілісекунд.

    

      

      
millis() точний до мікросекунди.

      
Крок millis() — 1 мс. Для коротших інтервалів беріть micros(): шаблон із відніманням той самий, але переповнюється вона вже за ≈ 71,6 хв.

      
Надрукуйте millis() і micros() двічі поспіль: різниця в мілісекундах майже завжди 0.

      Скетч для міні-лаби: src/main.cpp

#include <Arduino.h>
#define NONBLOCKING 0          // 0 — delay(), 1 — millis()

constexpr uint8_t LED_A = 4, LED_B = 5, LED_C = 15, BTN = 21;
uint32_t loops = 0, presses = 0;
uint32_t lastA = 0, lastB = 0, lastReport = 0;
bool ledA = false, ledB = false, ledC = false, wasDown = false;

void pollButton() {
  const bool down = digitalRead(BTN) == LOW;  // INPUT_PULLUP: натиснута = LOW
  if (down && !wasDown) {                     // зміна: щойно натиснули
    presses++;
    ledC = !ledC; digitalWrite(LED_C, ledC);
  }
  wasDown = down;
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_A, OUTPUT); pinMode(LED_B, OUTPUT); pinMode(LED_C, OUTPUT);
  pinMode(BTN, INPUT_PULLUP);
  lastA = lastB = lastReport = millis();
}

#if NONBLOCKING
void loop() {
  const uint32_t now = millis();
  pollButton();
  if (now - lastA >= 500) { lastA += 500; ledA = !ledA; digitalWrite(LED_A, ledA); }
  if (now - lastB >= 200) { lastB += 200; ledB = !ledB; digitalWrite(LED_B, ledB); }
  loops++;
  if (now - lastReport >= 1000) {
    lastReport += 1000;
    Serial.printf("loops/s=%u presses=%u\n", (unsigned)loops, (unsigned)presses);
    loops = 0;
  }
}
#else
void loop() {
  pollButton();
  digitalWrite(LED_A, HIGH); delay(500);
  digitalWrite(LED_A, LOW);  delay(500);
  ledB = !ledB; digitalWrite(LED_B, ledB);   // B мав би блимати раз на 200 мс…
  loops++;
  if (millis() - lastReport >= 1000) {       // той самий звіт, що й у неблокуючій версії
    lastReport += 1000;
    Serial.printf("loops/s=%u presses=%u\n", (unsigned)loops, (unsigned)presses);
    loops = 0;
  }
}
#endif

12 Командний виклик

    

      Командний виклик
      
Світлофор без delay()

      

        
Мета
Світлофор для машин і кнопка пішохода, жодного delay() у loop(). Часи станів: червоний 5 с → зелений 15 с → жовтий 2 с → знову червоний. Натискання на зеленому скорочує його: зелений гасне через 5 с від свого початку або одразу, якщо 5 с уже минуло. Натискання на червоному чи жовтому нічого не змінює.

        
Здати
Код (посилання на репозиторій або gist), 20-секундне відео, таблиця часів станів, виміряних за логом Serial, і одне речення: «де в коді можна було б заблокуватися і чому ми цього не зробили».

        
Ролі
    
          
  • Збирач збирає коло (3 LED + кнопка) і пише автомат станів світлофора;
    • 
          
  • Вимірювач пише журнал у Serial (кожен перехід з міткою millis()) і складає з нього таблицю часів «план / факт»;
    • 
          
  • Доповідач пише обробник кнопки (реакція на зміну, а не на рівень); на демо розповідає 3 хв;
    • 
          
  • Скептик перевіряє код за списком: немає delay() і while-очікувань, лише now - last, час в uint32_t, кнопка за зміною.
    • 
        

        
Критерії
    
          
  • Без блокувань: 2 — жодного delay() чи while-очікування; 1 — одне коротке (≤ 10 мс); 0 — більше.
    • 
          
  • Мінімальний зелений: 2 — за логом зелений ніколи не коротший за 5 с, а натискання після 5-ї секунди гасить його не пізніше ніж за 0,1 с; 1 — одне порушення; 0 — правило не працює.
    • 
          
  • Кнопка: 2 — помічено 20 з 20 натискань; 1 — 17–19; 0 — менше 17.
    • 
          
  • Таблиця і пояснення: 2 — план/факт для всіх станів і речення про блокування; 1 — чогось бракує; 0 — немає.
    • 
        

        
Ускладнення
Нічний режим: коли фоторезистор (міні-проєкт 1) показує темряву, жовтий блимає раз на секунду.

        
Термін
до сб 10.10, 10:00 (демо на занятті того дня)

ConcepTest 1 (питання 1 самоперевірки, E6): «Під час delay(2000) натиснули й відпустили кнопку. Що станеться?»

      
Відповідь і очікуваний розподіл
Очікувано: ≈ 35 % «чип зупинений», ≈ 40 % правильна «натискання пропаде», ≈ 20 % «стане в чергу», ≈ 5 % «перерве delay». Якщо правильних 30–70 %: 60 с суперечки двох студентів з різними відповідями, потім переголосування.

ConcepTest 2: «now >= last + interval і now - last >= interval — однакові?»

      
Відповідь і очікуваний розподіл
Очікувано ≈ 60 % «так». Розв’язка: віджет «Переповнення millis()», режими «за 500 мс до нуля» (зарано) і «за 1200 мс до нуля» (застрягла).

      
Знайди помилку (хв 46–55): три фрагменти, учасники пишуть у чат номер фрагмента (1–3) і що в ньому зламано:

    2. 
        
  2. uint16_t last; — після 65 535 мс now - last завжди величезне, тож LED «шаленіє» вже за хвилину після старту.
    3. 
        
  3. while (digitalRead(BTN) == HIGH) {} у loop() — очікування замість опитування, і світлодіоди стоять.
    4.

Що виправлено порівняно з LMS

    
    
      
  • Уточнення: «блокується лише те ядро або той потік виконання, де викликано delay()». LMS дає два варіанти, і правильний — другий: блокується лише задача loopTask. delay() = vTaskDelay(), і поки loopTask спить, те саме ядро 1 виконує інші задачі.
    • 
      
  • Опитування кнопки if (BUTTON_PIN == PRESSED). Так порівнюється номер піна з константою, а не стан піна. В Arduino: digitalRead(BUTTON_PIN) == LOW, бо з INPUT_PULLUP натиснута кнопка дає LOW.
    • 
      
  • Уточнення: рівень проти зміни. У прикладі LMS handle_press() викликається в кожному проході, поки кнопку тримають, тобто тисячі разів на одне натискання. Потрібна перевірка зміни (down && !wasDown), а згодом і debounce (урок 2.6).
    • 
      
  • Уточнення: int main() { while (true) … }. В Arduino-ESP32 main() не пишуть: ядро саме створює задачу loopTask, яка один раз викликає setup(), а потім нескінченно loop(). Сенс суперциклу той самий.
    • 
      
  • Уточнення: last_toggle = now. Працює, але накопичує дрейф, щойно прохід циклу буває довшим за 1 мс. Для рівної сітки — last_toggle += interval (розділ 04, «Детальніше»).
