C++ для мікроконтролера: обмеження і звички

Мова та сама, але пам'ять скінченна, а цикл не має права зависати. Розберемо, де живуть змінні, чому купа «кришиться» і що насправді роблять volatile, const і constexpr.

  • ≈ 25 хв читання
  • Потрібно: плата YD-ESP32-S3 і USB-кабель
  • Спершу: урок 1.3 (Blink)
Я це знаю → до самоперевірки

01 Навіщо це

Метеостанція на ESP32 справно працювала три доби, а на четверту перестала відповідати. Код ніхто не чіпав, помилок у моніторі не було. Винуватець — один рядок у loop(): String msg = "t=" + String(temp) + …. Тисячі дрібних виділень пам'яті поступово посікли купу на дрібні шматки, і одного дня для буфера просто не знайшлося суцільного місця.

На ноутбуці ви б цього не помітили: там гігабайти пам'яті й операційна система, яка за вами прибирає. На мікроконтролері ваш код — єдиний господар. Тому кожна звичка тут або береже ресурс, або тихо його з'їдає.

02 Після уроку ви зможете

  • пояснити, чому вбудований код уникає купи після старту, і показати фрагментацію на прикладі;
  • визначити за оголошенням, де лежить змінна (Flash, RAM, стек), і порахувати її розмір;
  • пояснити, що робить volatile і чого він не робить;
  • вибрати між const, constexpr і static та переписати delay() на millis().

03 Розминка: згадаймо

04 Головні ідеї

У плати три різні «склади» пам'яті

Flash — велика, переживає вимкнення, але писати в неї під час роботи незручно: тут код і константи. SRAM усередині чипа — швидка й невелика, стирається при вимкненні. У ній живуть глобальні змінні, купа (heap: пам'ять, яку програма просить уже під час роботи через malloc чи new) і стеки (stack: місце для локальних змінних функції, поки вона виконується). PSRAM — окрема мікросхема оперативної пам'яті в модулі: багато місця для великих буферів, але доступ іде через зовнішню шину й кеш.

Числа для нашого модуля: SRAM 512 КБ, Flash 16 МБ і PSRAM 8 МБ. SRAM у 32 рази менша за Flash, і саме її з'їдають погані звички.

ГоловнеЩо відоме до запуску, хай живе у Flash; SRAM — для того, що справді змінюється.

Купа кришиться: «вільно» ще не означає «можна виділити»

Уявіть парковку вздовж бордюру, куди приїжджають і від'їжджають машини різної довжини. Через день вільних метрів багато, але вони розкидані дрібними проміжками між машинами, і автобус уже не стане. Це фрагментація: malloc() потрібен суцільний шматок, а не сума дірок.

Друга біда — час: пошук місця триває щоразу по-різному. Тому правило таке: усе, що потрібно, виділіть один раз у setup(), а в loop() працюйте зі статичними буферами і стеком.

ГоловнеКупа корисна при старті; у циклі вона з часом кришиться, тож у loop() — без new, malloc і String-склейок.

Суперцикл: кожен прохід швидкий і нічого не чекає

loop() — як вахтер, що обходить двері: зазирнув, чи все гаразд, і пішов далі. delay(500) — це вахтер, який заснув на пів секунди: двері в цей час ніхто не перевіряє. Замість сну питайте годинник: «чи минуло 500 мс з минулого разу?» Відповідь займає мікросекунди.

uint32_t now = millis();
// працює й після переповнення
if (now - lastMs >= kBlinkMs) {
  lastMs = now;
  toggleLed();
}

На ESP32 loop() крутиться всередині задачі FreeRTOS, а delay() присипляє лише її: переривання і Wi-Fi живуть далі, але ваш цикл стоїть. Лічильник millis() переповнюється раз на ≈ 49,7 доби; віднімання беззнакових чисел це переживає, а порівняння now >= lastMs + kBlinkMs — ні.

ГоловнеКожна функція в суперциклі робить крок і одразу повертається; чекання замінює перевірка millis().

volatile означає «перечитуй щоразу» — і нічого більше

Переривання — сигнал від заліза (скажімо, натиснули кнопку), за яким процесор на мить кидає ваш код і виконує коротку функцію-обробник, ISR (interrupt service routine). Детально — в уроці 2.4; тут важливо одне: ISR може змінити змінну «за спиною» у loop().

Компілятор економить: якщо в циклі змінну ніхто не змінює, він прочитає її один раз у регістр процесора і далі дивитиметься лише туди. Але прапорець може змінити переривання, а регістр периферії — саме залізо. volatile забороняє цю економію: кожне звернення в коді — справжнє читання чи запис пам'яті.

Чого він не дає: атомарності. counter++ над volatile — це три окремі інструкції «прочитати, додати, записати», і переривання може вклинитися між ними. Для цього — коротка критична секція (на кілька інструкцій забороняє перериванням втручатися) або std::atomic.

Головнеvolatile — для регістрів заліза і прапорців з ISR; він не робить операцію атомарною і не синхронізує задачі.

const — «я не змінюю»; constexpr — «відомо ще під час компіляції»

const — обіцянка коду не змінювати значення. Де воно ляже, вирішує інше: чи відоме значення компілятору. const int kCalib = readCalib(); — константа, але її значення з'являється лише після старту, тож вона живе в RAM. constexpr вимагає, щоб значення було відоме компілятору: таблиця ляже у Flash, а одне число часто взагалі стає частиною інструкції.

static усередині функції — змінна, що пам'ятає значення між викликами: вона лежить у RAM поруч із глобальними, а не на стеку.

Магічне число — голе число в коді без імені, як 15 у digitalWrite(15, HIGH): незрозуміло, що воно означає, і легко забути виправити його в усіх місцях. constexpr uint8_t kLedPin = 15; дає йому ім'я і не коштує жодного байта.

ГоловнеПишіть constexpr для всього, що відоме наперед (піни, інтервали, таблиці); const — для «один раз обчислив і не чіпаю».

Детальніше: винятки, RTTI і STL у нашій збірці

Ядро Arduino-ESP32 2.0.17 компілює C++ з увімкненими винятками і вимкненим RTTI (-fexceptions -fno-rtti). Отже, typeid і dynamic_cast униз по ієрархії (той, що перевіряє тип під час роботи) не скомпілюються, а throw скомпілюється, але додасть коду й непередбачуваний час розкручування стека. У вбудованому коді помилку частіше повертають значенням: bool, код помилки, «порожній» результат.

STL не заборонений цілком. std::array, <algorithm>, <cstdint>, <limits> купою не користуються. Небезпечні контейнери, що ростуть самі: std::vector, std::string, std::map, std::function з великим захопленням. Якщо вже потрібен vector, зробіть reserve() у setup() і не виходьте за цей розмір.

Збірка ядра оптимізує за розміром, -Os. Саме тому приклад з volatile у розділі 05 — не теорія: ми скомпілювали його тим самим компілятором.

Детальніше: три способи ініціалізувати периферію

1. Явна init(). Конструктор лише запам'ятовує пін, а залізо налаштовує init(), яку ви викликаєте з setup(). Глобальні об'єкти створюються ще до старту ядра Arduino, тож pinMode у конструкторі — ризик.

class Led {
 public:
  constexpr explicit Led(uint8_t pin) : pin_(pin) {}
  void init() const { pinMode(pin_, OUTPUT); }
 private:
  const uint8_t pin_;
};

2. Ліниво, через локальний static. Ініціалізація при першому виклику. Зручно, але момент виконання неочевидний: перший виклик може статися будь-де, навіть у невдалий час.

3. Таблиця конфігурації constexpr. Налаштування — це дані у Flash, а одна функція їх застосовує. Помилки конфігурації ловить static_assert ще до прошивки.

struct PinCfg { uint8_t pin; uint8_t mode; };
constexpr PinCfg kPins[] = { {15, OUTPUT}, {21, INPUT_PULLUP} };
static_assert(kPins[0].pin != kPins[1].pin, "один пін двічі");
void initPins() { for (const auto& p : kPins) pinMode(p.pin, p.mode); }

У LMS приклад написано з .dir = … (позначені ініціалізатори). Це синтаксис C++20; наш GCC 8.4 у режимі gnu++11/gnu++17 приймає його як розширення.

Детальніше: що C++20 змінив у volatile

C++20 оголосив застарілими кілька операцій над volatile: ++/−−, складене присвоєння, ланцюжок a = b = c, volatile-параметри й значення, що повертаються. Складені присвоєння згодом «помилували», тож REG |= mask; — нормальний код. Застаріле ≠ заборонене: компілюється, новіші GCC дають попередження. Сенс зміни — чесність: v++ виглядає як одна дія, а це три.

    07 Типові помилки
    
    
    
      
    
        
    volatile int counter — і counter++ з ISR та з loop() безпечний.
    
        
    volatile лише забороняє кешувати значення. ++ — це «прочитати, додати, записати», і ISR може вклинитися посередині: одне збільшення загубиться.
    
        
    Подивіться асемблер counter++: три інструкції. Захистіть їх portENTER_CRITICAL(&mux) або візьміть std::atomic.
    
      
    
      
    
        
    Будь-який const лежить у Flash і не займає RAM.
    
        
    Важливо, коли відоме значення. const int k = analogRead(4); обчислюється після старту й живе в RAM.
    
        
    Зберіть проєкт і подивіться символ: xtensa-esp32s3-elf-nm -C .pio/build/<env>/firmware.elf | grep kCalib (програма лежить у ~/.platformio/packages/toolchain-xtensa-esp32s3/bin/). Літера b (.bss) означає RAM, r (.rodata) — Flash.
    
      
    
      
    
        
    STL на мікроконтролері заборонений повністю.
    
        
    Заборона стосується контейнерів, що самі ростуть у купі. std::array, <algorithm>, <cstdint> купи не чіпають.
    
        
    У проєкті esp32-s3-embedded-cpp немає жодного виклику malloc чи new, хоча він використовує <limits> і <cstdint> — див. results/heap-symbols-cpp.txt.
    
      
    
      
    
        
    new і malloc не можна використовувати ніколи.
    
        
    Один раз у setup(), без free — нормально: фрагментувати нічому. Шкодить чергування виділень і звільнень у циклі.
    
        
    Виведіть ESP.getMaxAllocHeap() після setup() і через годину роботи: якщо число не падає, купа здорова.
    
      
    
      
    
        
    Винятки (throw/catch) нічого не коштують, поки не кинуті.
    
        
    Навіть некинутий виняток тягне в прошивку код розкручування стека й таблиці; кинутий — працює непередбачуваний час. У нашій збірці винятки ввімкнені, але помилку краще повертати значенням.
    
        
    Зберіть скетч двічі: з одним throw std::runtime_error("x") і без нього. Порівняйте рядок «Flash: … used» у виводі pio run.
    
      
    
      
    
        
    delay() зупиняє весь чип, навіть переривання.
    
        
    На ESP32 delay() присипляє лише задачу з loop(). Переривання спрацюють, але реагувати на прапорець ваш цикл буде лише після сну.
    
        
    Лічіть натискання в ISR, а в loop() поставте delay(2000): лічильник росте, хоча друкується рідко.

    // Урок 2.1 · міні-лаба «Фрагментація купи». Arduino-ESP32 2.0.17 (espressif32@^7.1.0).
#include <Arduino.h>
#include <esp_heap_caps.h>

constexpr size_t   kBlockSize = 2000;          // блок, яким займаємо купу
constexpr size_t   kMaxBlocks = 200;
constexpr uint32_t kReserve   = 40 * 1024;     // лишаємо запас для USB, Serial і ядра
constexpr size_t   kBig       = 64 * 1024;     // набагато менше за free після кроку 3
// Лише внутрішня RAM: звичайний malloc() на платі з PSRAM запити > 4096 Б
// віддав би в PSRAM, і фрагментацію внутрішньої купи ми б не побачили.
constexpr uint32_t kCaps      = MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT;

void*  blocks[kMaxBlocks];                     // .bss: 200 вказівників по 4 Б
size_t count = 0;

void report(const char* step) {
  Serial.printf("%-16s free=%6u max=%6u\n", step,
                (unsigned)ESP.getFreeHeap(), (unsigned)ESP.getMaxAllocHeap());
}

void tryBig() {
  void* p = heap_caps_malloc(kBig, kCaps);
  Serial.printf("  malloc(%u) -> %s\n", (unsigned)kBig, p ? "OK" : "NULL");
  heap_caps_free(p);                           // free(nullptr) безпечний
}

void setup() {
  Serial.begin(115200);
  delay(3000);                                 // час відкрити монітор; у setup() це нормально
  report("1 start");

  while (count < kMaxBlocks && ESP.getFreeHeap() > kReserve) {
    void* p = heap_caps_malloc(kBlockSize, kCaps);
    if (p == nullptr) break;
    blocks[count++] = p;
  }
  Serial.printf("blocks: %u\n", (unsigned)count);
  report("2 filled");

  for (size_t i = 0; i < count; i += 2) { heap_caps_free(blocks[i]); blocks[i] = nullptr; }
  report("3 half freed");
  tryBig();                                    // вільно багато, але суцільного шматка немає

  for (size_t i = 1; i < count; i += 2) { heap_caps_free(blocks[i]); blocks[i] = nullptr; }
  report("4 all freed");
  tryBig();                                    // ті самі байти, але тепер одним шматком
}

void loop() {}

      Командний виклик
      
    Рефакторинг шкідливого скетчу
    
      
    
        
    Мета
    Переписати скетч нижче так, щоб він не блокувався, не кришив купу і не губив натискань. Поведінка та сама: LED на GPIO15 блимає 500/500 мс, кожну секунду в журнал пишеться рядок з часом і АЦП, натискання кнопки GPIO21 рахуються.
    
        
    Потрібно
    Стенд з уроку 1.3 і проєкту esp32-s3-embedded-cpp: LED через резистор 220 Ом на GPIO15, кнопка між GPIO21 і GND (внутрішня підтяжка INPUT_PULLUP).
    
        
    Здати
    Diff командного рішення (або посилання на PR у вашому форку platformio-projects) + рядки з монітора: ESP.getFreeHeap() і ESP.getMinFreeHeap() одразу після setup() і через 10 хвилин — для старого і нового скетчу.
    
        
    Ролі
      
          
    • Збирач: прибирає блокування — delay() → millis(); показує стенд на камеру;
      • 
          
    • Вимірювач: прибирає String-склейки — кільцевий буфер char[] + snprintf; знімає купу до і після;
      • 
          
    • Доповідач: прибирає магічні числа й глобальну «кашу» — constexpr-конфіг, клас або анонімний простір імен; пише пост із результатом;
      • 
          
    • Скептик: виправляє ISR (volatile, без Serial усередині, критична секція для лічильника) і перевіряє код інших за чеклістом нижче.
      • 
        
    
        
    Чекліст Скептика
    4 пункти перевірки
      
          
    1. У loop() немає delay() і порожніх циклів очікування.
      2. 
          
    2. У loop() немає String-склейок, new, malloc, push_back.
      3. 
          
    3. ISR: IRAM_ATTR, спільні змінні volatile, жодного Serial; читання й скидання лічильника в loop() — в одній критичній секції.
      4. 
          
    4. Кожне число в коді має ім'я (constexpr), крім 0 і 1.
      5. 
        
    
        
    Критерії
    0–2 бали кожен: (1) у loop() немає delay; (2) у loop() немає виділень у купі: getFreeHeap() і getMinFreeHeap() через 10 хв ті самі, що після setup(); (3) ISR коротка й коректна; (4) немає магічних чисел.
    
        
    Ускладнення
    Додайте static_assert, що піни LED і кнопки різні, і виміряйте найдовший прохід loop() через micros().

    #include <Arduino.h>

String history = "";
int count = 0;
bool pressed = false;

void isr() {
  pressed = true;
  count++;
  Serial.println("press!");
}

void setup() {
  Serial.begin(115200);
  pinMode(15, OUTPUT);
  pinMode(21, INPUT_PULLUP);
  attachInterrupt(21, isr, FALLING);
}

void loop() {
  digitalWrite(15, HIGH);
  delay(500);
  digitalWrite(15, LOW);
  delay(500);
  history += "t=" + String(millis()) + " adc=" + String(analogRead(4)) + "\n";
  if (history.length() > 2000) {
    Serial.print(history);
    history = "";
  }
  if (pressed) {
    Serial.println(count);
    pressed = false;
  }
}

    7 уточнень: розгорнути
    
      
      
    1. «Спільні змінні задач RTOS мають бути volatile». Для зв'язку між задачами volatile недостатньо: він не дає ні атомарності, ні порядку. Потрібні критична секція, std::atomic або черги FreeRTOS.
      2. 
      
    2. «C++20 оголосив застарілим volatile для багатопотоковості». Насправді застарілими стали окремі операції (++, складене присвоєння тощо), а складені присвоєння потім повернули.
      3. 
      
    3. «constexpr майже завжди у Flash, const — як вийде». Уточнено для ESP32: вирішує, чи відоме значення під час компіляції. Глобальний const з константним значенням теж лежить у Flash, const з обчисленим при старті значенням — у RAM, а скалярний constexpr часто взагалі не займає пам'яті.
      4. 
      
    4. «Уникаємо винятків і RTTI». Уточнено для нашої збірки: винятки ввімкнені, RTTI вимкнено, тож typeid і dynamic_cast униз по ієрархії не скомпілюються.
      5. 
      
    5. «Суперцикл — без ОС». На Arduino-ESP32 loop() — задача FreeRTOS, а delay() присипляє лише її.
      6. 
      
    6. Приклад з .dir = … — це синтаксис C++20; GCC 8.4 у наших режимах приймає його лише як розширення.
      7. 
      
    7. «Кілька кілобайт RAM». На нашій платі 512 КБ SRAM і 8 МБ PSRAM; принцип економії той самий, бо купа фрагментується за будь-якого розміру.
